# 话题底座 + 追剧 / 对照读 / 术语线术语包

日期：2026-09-26 状态：已批准设计，待实施计划
前置：本设计的一切产物都建立在一个新底座上 —— **活的主题注册表（topic registry）**。

## 0. 用户事实（决定取舍的前提）

- 实际用法：**读文章 + 顺手查词，从不复习**。因此凡依赖"用户会去复习"的机制（到期队列、提醒、SRS 升级、掌握后抽查）一律不在本设计范围内，也不得作为理由被引入。
- 文章是**一次性消耗品**：读完转已读、回主界面即弱化。不为消耗品建"随水平变化"的指标。
- 现有词汇闭环（memory / srs / Vocab 复习 tab）**保持原样**，本设计不碰它的行为与数据。
- 2026-09-26 当场确认两件此前悬空的事：① 侧边栏「标签」那一节由「话题」直接顶掉（§4）；② 存量回填按 200 篇跑（§10 第一条）。本设计因此不再有等用户拍板的开口。

## 1. Goal

1. **底座**：把每篇新入库文章归入一个"话题"，话题表由语料自己长出来，不预设清单。
2. **追剧（话题时间线）**：侧边栏按话题浏览；话题页顶部给一段中文"前情提要"。
3. **对照读**：读完一篇后，用一张窄卡并排展示"同一件事另一家怎么写"（标题 + 导语），并点破措辞里的立场。
4. **术语线**：话题页底部按词块共现自动排出"这条线躲不开的说法"，不需要人工标注。

## 2. Non-goals

- 不引入 embedding 模型 / 聚类库 / 任何 ML 运行时（与 rank.rs 当初"确定性、可解释"的取向一致）。
- 不改 rank.rs 的兴趣打分，也不改它使用的 tag 画像 —— **标签继续作为打分信号，只是不再作为浏览入口**。
- 不做多语言话题表、不做话题云图、不做话题订阅推送。
- 不重建已入库文章的正文/简介数据。

## 3. 底座：活话题注册表

### 3.1 数据

新表 `topics`：

| 列 | 说明 |
|---|---|
| `id` | TEXT PK |
| `name` | 中文话题名，如「美联储与利率」 |
| `blurb` | 一句话界定，喂给 LLM 用于消歧 |
| `key_terms` | JSON 数组，该话题的代表英文词，随归入累积 |
| `status` | `active` \| `dormant` \| `merged` |
| `created_at` / `last_seen_at` | RFC3339 |
| `merged_into` | 合并后指向主话题，可空 |

新表 `article_topics(article_id, topic_id)`，联合主键；每篇 1–2 个话题。
新表 `topic_recaps(topic_id PK, text, covers_until, generated_at)` —— 前情提要缓存。
新表 `compare_cards(article_id PK, payload_json, generated_at)` —— 对照卡缓存。
新表 `article_chunks(article_id PK, keys_json)` —— 该篇命中的词块键，供术语线统计。

迁移沿用 `db/mod.rs` 现有风格：`user_version` 逐版推进，当前最高 14；**本设计占 v16**（v15 已让给同期排在前面的 `2026-09-26-saved-sentence-design.md`，两份计划共用一套号避免撞车）。`CREATE TABLE IF NOT EXISTS`，不写回滚。

### 3.2 归入还是新立

每条新文章（或回填批次里的一篇）走**两段式**，避免把判定权全交给 LLM：

1. **便宜地挑候选**：拿文章 token 集（标题 + 正文前 600 字符）对每个 `active` 话题算重叠分。打分式定为 `|文章 ∩ 话题 key_terms| / |话题 key_terms|`（分母固定取话题侧规模：一个词表很长的话题不该因为词多就更容易被选中，只有"本文确实命中了它的多少词"才算数），取最高 5 个。纯 Rust，可单测。
2. **LLM 终判**：输入 = 标题、中文简介、5 个候选（name + blurb）；输出 = JSON：
   ```
   { "topic_ids": ["t12"],
     "new_topic": null | { "name": "...", "blurb": "...",
                            "key_terms": ["fed","rate",...],
                            "why_not_existing": "..." } }
   ```

硬约束（写进提示词并在解析层校验，不合规即视为归入失败、本篇留空待重试）：

- 只要有一个候选确实涵盖本文，**必须归入，不得新立**；归入与新立互斥。
- 新立只允许生成**大类**：能覆盖未来至少一个月同类报道的名字，不得是为本文临时造的具体事件名（不写「9 月 FOMC 决议」，写「美联储与利率」）。
- `why_not_existing` 必须逐个点名 5 个候选为什么不合适，空或含糊即拒绝新立。
- 新立名字与该话题库现有任何 active 名字共用 ≥ 2 个 `key_terms` 时拒绝新立，转为归入重合度最高的那个。
- 归入成功后把本文新出现的实义词并入该话题 `key_terms`（上限 60 个，超出时按低频淘汰）。

这一组的目的只有一个：**碎比错更难修**，所以判定要偏向归入。

### 3.3 防碎三件

1. **新立得贵** —— 见 3.2 的约束组。
2. **话题会凉**：`last_seen_at` 距今 > 45 天 → `status='dormant'`，退出候选池与侧边栏；`article_topics` 完整保留，翻旧线不受影响。沉降在一次刷新时以一条 UPDATE 完成，不需要后台任务。
3. **能捏回来**：`merge_topics(from_ids, into_id)` 重写 `article_topics`、合并 `key_terms`、`from.merged_into = into` 且置 `status='merged'`、作废旧 `topic_recaps`。提供 `list_near_duplicate_topics`（`key_terms` 重合度 top-N 的 pair）供界面提示"这两条像是一条"，一键合并。

### 3.4 回填与降级

完全复制 `fill_missing_tags` 的形状：`commands/articles::fill_missing_topics(limit)` → `feeds::enrich::fill_missing_topics(db, cfg, limit, on_progress)` + `db::articles_missing_topic(conn, limit)`。

- 刷新管线在补完简介/标签之后顺带跑一小批（与现有 enrich 同一位置）。
- command 层无 API Key 时返回 0（不报错、不弹窗）；enrich 层无 Key 时返回中文错误，与现有一致。
- 无 LLM 时话题功能整体为空态，首页/侧边栏不显示残缺内容。

## 4. 追剧：话题时间线

- **入口取代侧边栏「标签」那一节**：`Sidebar.tsx` 移除 `availableTags` 区块，改为「话题」，列出 `active` 话题按 `last_seen_at` 倒序，附未读数徽标。`selectedTags` 一套筛选状态换成 `selectedTopics`，经 `ArticleQuery.topics` 走 `article_topics` JOIN。
- **话题页**（`/topic/:id`）：该话题下文章按 `published_at` 倒序，复用 `ArticleRow` 与已读弱化；顶部是前情提要，不是文章。
- **前情提要**：取该话题最近 10 篇的 `title + summary_zh`，一次 LLM 调用写成 3–5 句中文（这条线发生了什么、语气变化、有没有反转），存 `topic_recaps`，`covers_until` 记覆盖到的最新文章时间戳。仅当"覆盖之后新增 ≥ 3 篇"才重算，否则复用缓存。无缓存或无 Key 时该区域整体不渲染（不留骨架、不显示英文兜底）。

## 5. 对照读：另一家怎么写

- **不做三栏并排全文。** 只比标题 + 导语，配一句中文点破措辞 —— 注意力要锁在选词上，不是比内容对错。
- **触发时机**：本篇 `read_completed` 为真之后，在 Reader 页尾出现一张窄卡；不在读之前挡道。
- **配对判据**（确定性，可单测）：同话题 + `published_at` 相差 ≤ 48 小时 + 来源不同 + 标题相似。标题相似定为**满足其一**：① 去停用词后共有关键词 ≥ 3 个；② 共有关键词数 / 较短那篇的实词数 ≥ 0.4。两个数字都是常量，供第 4 步实测后校准，不做成用户可配置项。按重叠降序取至多 2 篇，连同本篇最多三家；凑不齐就不渲染，不报错。
- **导语**：`content_text` 第一段，按现有段落切分取，截 ≤ 45 词；缺段则退到正文前 45 词。
- **点破**：一次 LLM 调用，输入各家标题 + 导语，输出 ≤ 2 句中文，指明谁在替读者下判断（带情绪/归责的词、被省掉的施事者），不做政治评价、不下"谁对"的结论。
- **缓存**：结果整张卡存 `compare_cards`，重读不重算。无 API Key 或无配对 → 不显示。

## 6. 术语线：话题的词块共现

- 数据来自 **3241 条词块表与真实文章正文的匹配**，不依赖 `chunks.json` 的 `labels` —— 实测 labels 只有 328 条带值（财经 20、时事 22、法律 8），撑不起术语包。
- 匹配复用前端既有通路：`wordLevels.ts` 已有带测试的最长词块匹配（lemma 归一 + 连字符/空格双向）。**不在 Rust 侧重写一遍**；改为 Reader 标注完成后把命中键写回 `article_chunks`。
- 话题页底部：取该话题下文章（限已入库集合）的 `article_chunks` 计数，排除只出现 1 次的键，按次数排前 12 条，展示「词块 + 中文释义 + 这条线里有几篇提到」。
- 已知边界：只有被打开过的文章会产生命中记录，因此术语线反映的是"你读过的这条线"。这是有意的取舍 —— 为未读文章专门跑一遍分词收益低，且对用户语义更弱。

## 8. 测试

- 纯函数单测（Rust）：候选重叠打分（长表不得霸屏）、归入/新立解析校验的每条拒绝分支、45 天沉降、合并后计数正确、配对判据的 48h 与词重叠边界。
- 前端 vitest：话题筛选的列表派生、术语线排序与"只出现 1 次"过滤。按现有约定按域归堆，不单开孤儿文件。
- DB 集成测试进 `db_tests.rs`。
- 验收前跑：`node scripts/stop-desktop.mjs` → `pnpm test` → `pnpm build` → `cd src-tauri && cargo test`；真机行为需 `pnpm dev:desktop` 验证（浏览器模式 invoke 不可用）。

## 9. 落地顺序

1. **底座**：`topics` / `article_topics` + 候选打分 + LLM 归入与约束校验 + 回填 command。先不开界面，用一次回填验证话题数量与近重情况（此时最能暴露"碎不碎"）。
2. **入口**：侧边栏话题节 + 话题页时间线（不含提要）。此时产品已可用。
3. **前情提要** + 术语线（`article_chunks` 回写与统计）。
4. **对照卡**。

理由：第 1 步是全案唯一的高风险项（LLM 判定质量与碎裂），必须先单独验证再往上盖界面。依赖关系：§4 追剧要第 1、2 步都有；§6 术语线要第 1 步的话题归入加第 3 步的词块回写；§5 对照读只要第 1 步的话题归成立即可，因此排最后，且可以整块砍掉而不影响前三步的价值。

## 10. 验收标准

- [ ] 回填 200 篇后，active 话题数 < 60，且近重话题可被 `list_near_duplicate_topics` 检出并一键合并
- [ ] 同一件事的两周报道归入同一话题；新立话题名均为可覆盖一个月的大类
- [ ] 侧边栏不再出现标签节，话题节可直接筛出该话题文章，未读数正确
- [ ] 话题页顶部为中文前情提要，3 篇以内新文章时不重算（命中缓存）
- [ ] 读完一篇（`read_completed`）后，存在配对时页尾出现对照卡，含 ≤ 3 家标题 + 导语与一句中文点破；无配对或无 Key 时整卡不出现
- [ ] 话题页底部术语线按共现次数排出词块，条目在文章里的出现次数 ≥ 2
- [ ] 无 API Key 时：以上 LLM 产物全部安静缺席，刷新与阅读不报错
- [ ] `pnpm test` / `pnpm build` / `cargo test` 全绿

## 11. 已知风险

- **归入判错比判碎好修**，但错也会累积成"什么都在美联储名下"。第 1 步回填后的近重与规模分布就是用来发现这个的，必要时把新立约束放宽一档（阈值可调，写死在常量里便于改）。
- **导语取第一段**依赖正文抽取干净；个别源会把记者署名行当首段。实施时若命中率低，退到"前 45 词"并在 spec 追加实测结果。
- 对照卡的中文点破由 LLM 生成，可能写得空泛（"两家措辞不同"）。提示词需强制"点名具体词 + 说清谁在归责"，否则不出卡。
